# Graph operation implementation questions

Prepared on 1 October 2026, before implementation changes, and revised to incorporate the user's permission to replace existing feature implementations completely. Existing APIs, wire formats, guest entrypoints, storage layouts, task structure, libraries and build integration may change. Backward compatibility with Beacon LOAD, current binaries or internal interfaces is not a requirement of this plan; a compatibility adapter is not a default work item. The documented protocol behavior, WebAssembly application model, embedded constraints and evaluation in `sim_env` remain the design inputs.

The questions below concern the replacement design and remain open unless an answer is recorded explicitly. Suggested starting points are proposals, not decisions inferred from silence. The companion [implementation plan](graph_operation_implementation_plan.md) and [test catalogue](graph_operation_test_plan.md) can be reviewed without choosing every parameter now. Existing code supplies examples and hazards to consider, rather than constraints on the new architecture.

The baseline is the [shared mechanisms](../../../Thesis/protocol%20specs/graph_operation_shared_mechanisms.md), [node addition v2](../../../Thesis/protocol%20specs/node_addition_protocol_v2.md), five derived protocols, and [implementation notes](../../../Thesis/protocol%20specs/graph_operation_implementation_notes.md). Questions concern their concrete realization or an explicitly identified extension. Receiver-first activation, full cleanup scope, immutable requests, historical success, and bounded admission are already specified; they are not open choices.

## Decisions needed before interfaces and storage are fixed

| ID | Implementation question | Why it is unresolved and what depends on it | Proposed starting point for review |
|---|---|---|---|
| Q01 | Which device and usable RAM/flash budgets are required, with or without PSRAM? What are the maximum resident nodes, incident channels, concurrent operations, payload sizes, and retained results? | “ESP32-like” is not a capacity specification. Admission, pool sizes, runtime selection and acceptance thresholds depend on this; neither current host nor embedded defaults establish these requirements. | Define a shared configurable resource profile from the intended workloads and selected board, then measure it on both ports. |
| Q02 | Is the first release crash-stop only, or must devices/orchestrator recover after reboot? | A7 and shared assumptions exclude restart/takeover. Simulator reboot exists but supplies no protocol recovery. | Preserve crash-stop for conformance. Treat reboot recovery, persistent identities and reconstruction as a separately specified extension. |
| Q03 | Who allocates operation and instance identities, what are their widths/scopes, and what prevents collision, reuse, or rollover while old traffic exists? | The protocol requires uniqueness, not numeric ordering or any existing integer layout. | Design protocol identities independently of internal record handles; select widths from lifetime, traffic and storage bounds, with explicit exhaustion and old-traffic isolation rules. |
| Q04 | What protocol joins O's authorization records to Kc/Ki reservations so removal gets complete incidence even when commands are delayed? How are abandoned pre-acceptance reservations handled? | M1 abstracts a consistent distributed admission boundary; the models do not implement it. A fresh local registry scan alone cannot discover an authorized edge still in transit. | O serializes conflicting authorizations, records all incident reservations before dispatch, and supplies verifiable scope/fence evidence. Kc/Ki atomically reserve local capacity and validate authority. Refine this algorithm before coding it. |
| Q05 | Which mechanism rejects obsolete control, callbacks, handles, and data after record retirement and later binding reuse? | E5/M6 require isolation; neither binding versions nor a session protocol are mandated. Channel tuple matching and a fresh removal opId alone are insufficient. | Carry an unambiguous creation/incarnation reference throughout the control and data paths. Compare bounded tombstones, proven retired prefixes, or an explicitly designed session barrier; do not use the highest ID seen as a retired prefix. |
| Q06 | How long is detailed operation evidence retrievable, who authorizes retirement, and what does a query return after authorized retirement? | Shared M7 requires bounded reserved result storage and separates detailed evidence from rejection records. No retention policy or retrieval-after-retirement response is defined. | Bound result slots and reject/defer admission when full. Move detailed history to O when the selected policy permits; retain safe obsolete-command rejection independently. A TTL alone is not evidence that old traffic disappeared. |
| Q07 | How are source revisions scoped and compared, including wraparound, delayed failure/READY reports, and local callbacks? | M2 requires matching, ordered evidence; the formal abstraction does not choose a revision representation. | Per-owner, per-object evidence ordering with a creation reference. Define overflow and stream retirement; never compare unrelated streams as one global sequence. |
| Q08 | What wire schema, encoding, transport, maximum frame size, fragmentation policy, authentication, and artifact integrity checks will realize authorized immutable requests? | The protocol specifies meaning and authority, but not a codec or transport. Existing CBOR/TCP choices are replaceable. | Compare bounded encoding and transport designs against RAM, flash, parsing cost and fault-injection requirements. Select one implementation after a small prototype; distinguish reception, acceptance and completion without adding an application READY exchange. |
| Q09 | How will new management API and manifest versions declare supported operations, contracts and limits, and reject incompatible requests? | Replacement permission removes the need to preserve old LOAD semantics, but supported-version/capability behavior for the new interfaces still needs definition. | Define one explicit six-operation API and manifest contract shared with the simulator's O client. Reject unsupported versions/features before allocation. Rebuild fixtures for this API; include no legacy bridge unless a separate requirement is introduced. |
| Q10 | Is the public predicate language Boolean-only initially, or must `atLeast` and `percent` be supported? What are expression/group size and nesting limits? | V2 offers optional shorthand, but the revised verification intentionally checks Boolean predicates only. Rounding, empty groups and numeric encoding need a concrete schema if shorthand is accepted. | Bounded positive Boolean expression representation. Either reject shorthand explicitly or normalize it with separate validation and equivalence tests. |

## Decisions needed before runtime and endpoint work

| ID | Implementation question | Why it is unresolved and what depends on it | Proposed starting point for review |
|---|---|---|---|
| Q11 | What new guest ABI and instance-scoped port/handle API support dynamic bindings, multiplicity, revocation, and unavailable/full/empty results? | The LaTeX design specifies ports and bindings but leaves their API open. Existing static interface arrays and guest binaries need not be retained. | Design stable declared ports, revocable binding handles and bounded change notification together; compile the example workloads against that ABI and validate binding support at admission. |
| Q12 | What guest initialization, entry, termination and cancellation contract supports inert preparation and truthful confirmation of actual execution? | M3/M5 require separate preparation and execution, but prescribe neither `setup`/`main_app` names nor a runtime integration. | Define allowed initialization effects and runtime entry instrumentation before selecting an engine. Test missing entrypoint, failed entry, trap, quick return and cancellation between dispatch and entry; guest liveness is a separate observation. |
| Q13 | Which ownership and reclamation design protects registry records, buffers, guest access, I/O and callbacks during cleanup? | M6 requires truthful closure but does not prescribe shared queues, reference counting, cancellation/join or an allocator. | Compare single-owner records with explicit handoff against bounded shared references where sharing is needed. Choose a representation whose quiescence and release can be demonstrated; stuck access remains charged and unresolved. |
| Q14 | Which execution model provides consistent local decisions, independent runtime/endpoint progress and bounded timer/cleanup service within the CPU and stack budget? | A6/P2 constrain observable progress, not pthreads, a central monitor queue, worker count or a particular locking scheme. | Prototype short event-driven control transitions with independent bounded runtime/endpoint work. Determine worker counts, queue policies and synchronization from progress and resource measurements; never hold a shared decision lock across guest execution or remote waits. |
| Q15 | What node/channel/removal/response allowances and retry schedules fit the target workload? How are exact-deadline events and time-counter overflow handled? | M7 fixes owners/start events and forbids reset by retries; it supplies no numerical bounds. | Injectable monotonic clock; treat addition success as requiring `now < deadline`; derive durations from measured work/delivery/handler bounds. Review this exact-boundary convention before implementation. |
| Q16 | What happens to partially completed artifact transfer and memory reservations on local/remote rejection or parsing failure? | Platform preparation is intentionally abstract; preparation may already have allocated or dispatched work. | A bounded staging owner and cleanup obligation for every partial allocation; pre-acceptance validation has a separate bounded workspace. Do not report allocation-free rejection after managed work begins. |
| Q23 | Which embedded WebAssembly engine and host/target integration can meet the new ABI, execution-entry, cancellation, memory-limit and footprint requirements? | WebAssembly is part of the documented application model; WAMR and its present wrappers are implementation choices that may be replaced. | Evaluate candidate engines or integration changes using a small prepare/start/cancel/close prototype and footprint measurements. Reuse WAMR only if it satisfies the selected contracts; rebuilding example modules is permitted. |

## Decisions needed for management and application evaluation

| ID | Implementation question | Why it is unresolved and what depends on it | Proposed starting point for review |
|---|---|---|---|
| Q17 | What are the cancellation, separately authorized reconciliation, query and result-update schemas, especially when multiple requests target one already-cleaning object? | Cleanup is specified, but management initiation, correlation and later retry policy are not implemented. Removal and originating addition have different opIds and outcomes. | Keep each request's result independently correlated; share owner cleanup work safely and attribute closure to the exact binding. Reconciliation must not silently restart an exhausted original allowance. |
| Q18 | Which channel contracts are required initially: overflow policy, ordering, expiry, duplicate handling, producer/consumer obligations and completion boundary? | `kaos_design.tex` provides candidate measurement and command profiles, not final policies. The current unreliable queue path does not limit the choices. | Select the minimum contracts required by the workloads, then choose buffer and transport mechanisms to realize them. Define return-edge application outcomes where needed; never infer actuator execution from transport success. |
| Q19 | Which clocks and timestamp provenance support data freshness across devices? | Local monotonic operation deadlines need no synchronization; acquisition-age guarantees do. The simulator's shared host clock can hide this difference. | Specify acquisition time and clock uncertainty separately from queue residence; test skew and stale/future timestamps. Do not use host timing as an implicit device guarantee. |
| Q20 | For ventilation, what are the intervals, plausible-input rules, minimum sensing/actuation, nominal/degraded/unavailable criteria, fallback and maximum fallback duration, and escalation conditions? | `fault_tolerance.tex` explicitly leaves these values open. Holding an old setpoint is not an agreed safe policy. | Parameterized workload tests with service acceptance blocked until criteria are supplied; keep graph-protocol correctness testable independently. |
| Q21 | What room/actuator model fidelity is necessary, and are hardware-bound sensing and local feedback represented as mocks, WASM nodes, or physical devices? | The selected ventilation application needs a physical-process model for service claims; sim_env has none. | Deterministic sensor/actuator fixtures first, then a justified plant model; maintain peripheral placement constraints. |
| Q22 | Does the evaluation require only the six specified operations, or also migration, live node replacement, reliable channels and autonomous recovery? | Older LaTeX discusses these graph/runtime capabilities; v2 excludes migration, live node replacement and in-place rebinding. This is separate from replacing the KaOS implementation, which the user has allowed. | Scope this plan to six operations plus their cleanup/reporting interfaces. Treat migration and recovery examples as future extensions, not already verified tests. |

Answers to Q01, Q02 and Q20 were requested during preparation. No answer is assumed in these documents. Q03–Q09, Q11–Q17 and Q23 must be resolved before their production interfaces are fixed, but do not prevent deterministic fixtures or small architecture/runtime prototypes. Reuse versus replacement is an implementation assessment within the user's stated scope, not another permission question. Q23 is appended without renumbering the existing references.

## Already resolved by the materials

Do not reopen these as implementation preferences: one live binding per complete directed channel identity; no reuse while cleanup is unresolved; preparation independent of guest execution; commit before activation; receiver ACTIVE evidence before sender authorization; separate dispatch/execution/STARTED acceptance; no extra O acknowledgement phase; every intended object in cleanup; no timeout-as-cleanup; optional work continues after historical node success; finite admission and independent progress. The plan records sources and reconciles older terminology.
